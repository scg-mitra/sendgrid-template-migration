# AGENTS.md

Context and coding standards for AI agents working in this repository: a Go [Wails v3](https://v3.wails.io) desktop app with a React + TypeScript frontend in `frontend/`.

---

## 1. Core Development Commands

Run these exact commands before committing any changes. On Linux the Go commands need `-tags gtk3` (the app builds against GTK3 + WebKit2GTK 4.1), and Go only compiles once `frontend/dist` exists, so build the frontend first.

### Go
- **Format & Tidy**: `go fmt ./... && go mod tidy`
- **Static Analysis & Linting**: `golangci-lint run --build-tags gtk3 ./...`
- **Unit Tests (with Race Detector)**: `go test -race -tags gtk3 -v ./...`
- **Single Test**: `go test -race -tags gtk3 -v -run TestName .`
- **Benchmarking**: `go test -tags gtk3 -benchmem -run=^$ -bench=. ./...`
- **Build**: `go build -tags gtk3 -v -o /dev/null .`

### Frontend (run in `frontend/`)
- **Install**: `npm ci`
- **Lint**: `npm run lint` (oxlint; must report no warnings, since CI shows them as annotations)
- **Type-check & Build**: `npm run build` (`tsc -b` then `vite build` into `frontend/dist`, which the Go binary embeds)

### Bindings
- **Regenerate** after changing any exported method or type on the `App` service in `app.go`: `make bindings`
- CI fails if `frontend/src/bindings` is out of date, so commit the regenerated files.

`make lint` and `make test` run the Go and frontend steps together.

## 2. Project Architecture & Packaging

- **Current Layout**: the Go app is a single `main` package at the repository root (see the file table in README → Development). Follow the layout below when adding new packages.
- **Frontend Layout** (`frontend/src/`):
  - `screens/`: the app's screens and dialogs.
  - `components/ui/`: [shadcn/ui](https://ui.shadcn.com) components. Add new ones with `npx shadcn@latest add <name>` rather than writing them by hand.
  - `lib/`: small shared helpers (`format.ts`, `utils.ts`).
  - `api.ts`: the only module that imports the generated bindings and `@wailsio/runtime`; the rest of the UI imports from `@/api`.
  - `bindings/`: generated by `make bindings`. Never edit by hand.
- **Directory Layout**:
  - `cmd/`: Entry points only (thin `main.go` files responsible for config parsing, dependency wiring, and OS signal shutdown).
  - `internal/`: All application business logic, domain services, storage, and transport layers. Never expose code here externally.
  - `pkg/`: Only code explicitly intended to be imported by other third-party projects.
- **Package Design**:
  - Name packages by what they provide, not what they contain (e.g., `user`, `postgres`, `httpclient`, never `utils`, `helpers`, `common`, or `models`).
  - Avoid cyclic dependencies; use unidirectional dependency flow (`cmd` -> `transport` -> `service` -> `repository`).

## 3. Idiomatic Go Conventions

### Interfaces
- **Accept interfaces, return structs**: Functions and constructors should take interfaces as parameters and return concrete types (`*MyService`).
- **Keep interfaces small**: Target 1 to 3 methods (e.g., `io.Reader`, `io.Closer`). Define interfaces on the **consumer** side, not on the provider/producer side.

### Error Handling
- **Wrap errors with context**: Always wrap when bubbling up: `fmt.Errorf("fetching user %s: %w", id, err)`.
- **Inspection**: Use `errors.Is(err, ErrNotFound)` for sentinel errors and `errors.As(err, &targetErr)` for typed errors. Never match error strings with `strings.Contains`.
- **Zero Panic Policy**: Never use `panic` or `recover` in application code or library packages. Return explicit errors. `panic` is only permissible in `cmd/` entrypoints or `init()` for static regex/template compilation failures.

### Concurrency & Context
- **Context First**: Pass `ctx context.Context` as the very first argument of functions doing I/O, database queries, or long computations. Never store `context.Context` inside a struct.
- **Goroutine Lifecycles**: Never launch a fire-and-forget goroutine (`go func()`). Every goroutine must have an explicit exit trigger (via `context.Done()`) and be coordinated with `sync.WaitGroup` or `golang.org/x/sync/errgroup`.
- **Race Detection**: Always run tests with `-race`. Protect shared mutable state with `sync.Mutex` / `sync.RWMutex` or channel-based actor models.

### Memory & Performance
- **Preallocate collections**: Always provide capacity hints when size is known: `make([]T, 0, len(items))` and `make(map[string]T, len(items))`.
- **Pointers vs. Values**:
  - Pass structs by value for small, immutable data (<= 64 bytes).
  - Use pointers when mutation is necessary, for large structs, or when the struct contains a lock (`sync.Mutex`). Never copy a struct containing a mutex.

## 4. Frontend Conventions (React & TypeScript)

Apply these to all new and modified frontend code. Existing screens such as `ConnectScreen.tsx` (~470 lines) predate the size limits: split them when you make substantial changes to them, not in unrelated commits.

### Project Specifics
- **Stack**: React, TypeScript (strict), Tailwind CSS v4 and shadcn/ui, built with Vite. Prefer existing shadcn components and Tailwind utilities over custom CSS or new dependencies.
- **Generated code**: `components/ui/` (shadcn) and `bindings/` (Wails) are exempt from the size, folder and export rules below. Keep shadcn edits minimal so components can be re-added with `npx shadcn@latest add`.
- **Backend calls**: go through `@/api`. Calls are async and can reject with a `CancelError`; handle both.

### File Size & Modularization
- **150-line limit**: no component file over 150 lines. Decompose it as it approaches the limit.
- **Render block ceiling**: if a `return (...)` exceeds 40 lines or nests more than 3 levels of elements/components, extract those sections into child components.
- **One component per file**: never declare helper components at the bottom of a file. Every component gets its own `.tsx` file.
- **Component files export only components**: oxlint's `react/only-export-components` rule (needed for fast refresh) warns on anything else. Move `cva` variants, constants, config arrays, table columns and validation schemas into an adjacent `.constants.ts` or `.helpers.ts` file (shadcn's equivalent is `components/ui/toggle-variants.ts`).

### Directory-Based Decomposition
When a component needs sub-components or complex logic, turn it into a feature folder:
```text
ComponentName/
├── ComponentName.tsx         # Main entry point (strictly layout & prop passing)
├── ComponentNameHeader.tsx   # Extracted sub-component
├── useComponentName.ts       # Extracted state & effect logic
├── ComponentName.types.ts    # Extracted interfaces/types
└── index.ts                  # Barrel export (export * from './ComponentName')
```

### Components
- **Function declarations**: declare components with `function`, never top-level arrow functions, `React.FC` or `React.StatelessComponent`.
  ```tsx
  export function UserProfile({ userId }: UserProfileProps) { ... }
  ```
- **Named exports only**: no default exports.
- **Presentational components**: keep `.tsx` files focused on layout. Put business logic, backend calls and state in custom hooks.

### TypeScript & Type Safety
- **Never use `any`**: use `unknown` with type guards, precise `interface`/`type` definitions, or generics. Use the generated binding types from `@/api` for backend data.
- **Props**: define an `interface` or `type` directly above the component (or in a `.types.ts` file if shared).
- **Event handlers**: use explicit React event types (`React.MouseEvent<HTMLButtonElement>`, `React.ChangeEvent<HTMLInputElement>`).
- **Discriminated unions** for multi-status state, rather than several boolean flags:
  ```ts
  type FetchState<T> =
    | { status: 'idle' }
    | { status: 'loading' }
    | { status: 'success'; data: T }
    | { status: 'error'; error: Error };
  ```

### Hooks & State
- **Custom hooks**: extract state logic, async calls, event handlers and data transformations into `use<Feature>.ts` hooks.
- **Minimize `useEffect`**: don't use it to derive state or respond to user events. Compute derived values during render.
- **Functional updates** when new state depends on the old: `setCount(prev => prev + 1)`.
- **Complete dependency arrays**: oxlint enforces `react/exhaustive-deps`. Never disable it without a comment explaining why.

### Rendering & Performance
- **Keys**: use stable, unique IDs (e.g. template IDs) for list `key` props, never the array index unless the list is static.
- **Pragmatic memoization**: use `useCallback`/`useMemo` only for callbacks passed to memoized children or genuinely expensive calculations.
- **Falsy values**: use `items.length > 0 && ...` rather than `items.length && ...`, and prefer `?.` and `??`.

### Imports & Styling
- **Import order**, with a blank line between groups:
  1. External libraries (React, Radix, `lucide-react`, ...)
  2. Internal `@/` imports (`@/components/...`, `@/screens/...`, `@/api`, `@/lib/...`)
  3. Relative imports and styles
- **Use the `@/` alias** rather than `../` paths.
- **Class names**: combine conditional classes with `cn()` from `@/lib/utils` (the `cn` package, a drop-in for `clsx` + `tailwind-merge`), not ternary string concatenation.

## 5. Code Pattern Examples

### Table-Driven Tests
```go
func TestParseVersion(t *testing.T) {
    t.Parallel()

    tests := []struct {
        name    string
        input   string
        want    Version
        wantErr bool
    }{
        {name: "valid semver", input: "v1.2.3", want: Version{Major: 1, Minor: 2, Patch: 3}, wantErr: false},
        {name: "empty string", input: "", want: Version{}, wantErr: true},
    }

    for _, tt := range tests {
        tt := tt // pin variable for parallel test runs in older go versions
        t.Run(tt.name, func(t *testing.T) {
            t.Parallel()

            got, err := ParseVersion(tt.input)
            if (err != nil) != tt.wantErr {
                t.Fatalf("ParseVersion() error = %v, wantErr %v", err, tt.wantErr)
            }
            if got != tt.want {
                t.Errorf("ParseVersion() = %+v, want %+v", got, tt.want)
            }
        })
    }
}
```

### Resource Cleanup
```go
// Always check error on acquisition before deferring cleanup
f, err := os.Open(path)
if err != nil {
    return fmt.Errorf("opening file: %w", err)
}
defer f.Close()
```

## 6. Changelog & Releases

`CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Each version's section is published as its GitHub Release notes, and a tag build fails if the section is missing or empty.

- **Record every user-facing change** under `## [Unreleased]` in the same commit as the change.
- **Group entries** under `### Added`, `### Changed`, `### Fixed`, `### Removed` or `### Security`. Leave out empty headings.
- **Write for app users**: describe what changed for them, not how the code changed. One bullet per change, in plain language.
- **Skip internal-only changes**: refactors, tests, CI and tooling don't need entries unless they affect users.
- **Never edit released sections** unless asked. Never rename `[Unreleased]` to a version or create tags yourself; the maintainer cuts releases (see README → Releases).
- **Preview notes** with `packaging/release-notes.sh <version>`.

## 7. Agent Boundaries

| Category | Rules |
| :--- | :--- |
| **Always Do** | Run `golangci-lint` and `go test -race` on any modified package before returning. |
| | Run `npm run lint` and `npm run build` in `frontend/` after any frontend change, with no lint warnings. |
| | Run `make bindings` after changing the `App` service in `app.go`, and commit the result. |
| | Add table-driven unit tests for every newly added function or modified edge case. |
| | Keep public exported identifiers documented with complete Go doc comments (`// FunctionName ...`). |
| | Add a `CHANGELOG.md` entry under `## [Unreleased]` for every user-facing change. |
| **Ask First** | Adding external dependencies to `go.mod` (prefer the Go standard library first). |
| | Adding npm dependencies to `frontend/package.json` (shadcn components and their Radix peers excepted). |
| | Bumping GitHub Actions to a new major version (check its release notes for breaking changes first). |
| | Changing exported function signatures in public API surfaces (`pkg/`). |
| | Creating or altering database schemas and migration scripts. |
| **Never Do** | Never swallow errors (`_ = doSomething()`) without an explicit comment explaining why. |
| | Never use `context.Background()` or `context.TODO()` in non-root functions. |
| | Never check in binaries, test cover profiles (`*.out`), or unformatted files. |
| | Never commit `frontend/dist/` or `frontend/node_modules/`, or hand-edit `frontend/src/bindings/`. |
| | Never bypass lock synchronization to silence race detector warnings. |
